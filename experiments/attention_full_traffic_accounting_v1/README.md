# Full-context verify attention: traffic accounting

The official task requires every key and value. For the previously profiled B32, context 80,000, verify-8 case, this diagnostic reconstructs the exact CUDA RNG length draw for reference seed 4319. The reference creates `torch.Generator(device='cuda').manual_seed(seed)` and draws the 32 lengths before any other random operation. `driver.py` reproduces those first draws without allocating the large cache; the sampled lengths and three additional seeds are in `modal.log`. Run `ap-CjEELOkZ2aZJyB9R1KqmUV` completed successfully.

For seed 4319, old-context lengths sum to 2,557,656 rows. Each row has two KV heads, 64 FP8 bytes per head, for each of K and V. Reading every old-context K and V once is therefore 2,557,656 × 2 × 2 × 64 = **654.760 MB** of logical payload. At page size one, reading one 32-bit page-table index per row adds **10.231 MB** of logical metadata; the eight newly written rows per request add at most 65,536 bytes of K/V payload. Actual traffic depends on caching, reuse, coalescing, transaction granularity and implementation; these numbers are a work accounting model, not a strict lower bound on HBM traffic or latency.

The archived NCU run `attention_current_verify32_ncu_v1/tables_ncu.log` on this seed and shape reported **669.45 MB device-memory reads**, plus 4.71 MB writes and about 180.26 µs kernel duration in the separate basic capture. The NCU source SHA-256 was `ffc1c6bb4e95aa30390858eab4c43dbd592b2884b4fe3e54412282eaafdbebaa`; diffing it against the current best `554adb3886491fa686e950773b2d5c5cc759377eae0f3a7d3abf9f15fd353293` shows only an additional dispatch plan for batch-16 sliding decode, not this full verify kernel or plan. The runs were not paired and NCU replays with unlocked clocks. The 669.45 MB figure is about 2.24% above the logical old-context KV payload and 0.67% above the simple KV-plus-index sum, but this residual cannot be assigned to redundant traffic: L2 hits, output writes, page-table accesses and counter aggregation differ from the model.

An earlier independent synthetic random-gather experiment (`h200_gather_bw_v1`) measured 3.64 TB/s for 2.56 million K/V rows, including its own graph timing. Dividing this sample's 654.760 MB logical payload by that measured rate gives approximately **180 µs**, close to the NCU number. This is an empirical comparator, not a lower bound: hardware clocks, launch overhead, cache residency, input layout and concurrent work differ. Together these measurements weaken the case for a large gain from removing redundant K/V reads in this particular kernel. Prioritize reducing latency-bound sliding cases, improving actual gather throughput, or a new scheduling/dataflow method; do not assume sparse attention, coarser KV quantization or cross-call caches are allowed by the task.
