# MoE streaming load depth screen

This diagnostic compares four and eight independent 16-byte global loads per thread on the same active expert weight and scale tensors, with cold-L2 graph replay on the public H200 image. The hypothesis is that additional outstanding loads may raise achievable streaming bandwidth relative to the earlier four-load probe. It measures a synthetic read, not the MoE output or challenge score; improvements here require a separate kernel implementation and full correctness and judge evaluation.

The experiment covers batch sizes 16 and 32 with seed 419 and two launch geometries. `driver.py` derives from `dev/modal/drv_moe_stream_floor.py`; it measures the current scored MoE source as a reference and reports each streaming configuration separately. The application is bounded by the runner's 300-second timeout and uses the same local GPU-job lock as Forge. Results and failures are recorded in `modal.log`.

The H200 run completed successfully (`ap-t5rbtZomLdAZDFhfJFqml9`). At batch 16, four loads took 105.98/106.18 µs versus 114.59/113.97 µs for eight, for the 264×512 / 528×256 geometries. At batch 32 the corresponding times were 118.77/119.38 µs versus 128.91/128.64 µs. The scored kernel measured 108.24 and 129.54 µs respectively in this run. Eight-load streaming was therefore about 7–9% slower here; do not pursue this particular unrolling as a direct optimization based on these results. Measurements are sequential, one seed, and a synthetic stream rather than paired full-kernel validation; they do not rule out TMA, different layouts, scheduling, or other memory methods.
