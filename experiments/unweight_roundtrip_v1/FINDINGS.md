# Unweight lossless codec round trip on H200

Upstream Unweight commit `db0e6d3d4505cf71379f6b9b4567acf598bc186c` and ThunderKittens `6fd51f22b5489c544e4f33fb1a21b3d39a79984a` were built as a shared library during a CPU image-build step using the public CUDA 13 image. H200 app `ap-x5aKHSjCZS6D1HvKjLJ7sv` exercised the actual upstream statistics, Huffman table construction, tile metadata, encoding, and full decoding APIs. The driver compared raw int16 views of every input and output BF16 bit.

At public reference weight seed 5151, QKV `[2304,8192]` and pooler `[4096,8192]` each had zero mismatched bits. A 512×512 Gaussian tensor with injected positive/negative zero, subnormal patterns, infinities and NaN bit patterns also had zero mismatches. QKV component bytes: 18,874,368 sign/mantissa + 6,089,104 encoded + 86,336 verbatim + 73,728 metadata + 589,824 row offsets = 25,713,360 bytes vs 37,748,736 BF16 bytes (~68.12%). Pooler: 33,554,432 + 10,826,368 + 147,136 + 131,072 + 1,048,576 = 45,707,584 bytes vs 67,108,864 (~68.11%). These totals exclude small palette/decode tables, alignment, transient allocation and prepare costs; they are codec storage measurements, not timed-call traffic or a speed result. Raw details are in `screen.log`.

Our first app failed to load the shared library because the CUDA driver library was not linked (`link-failure.log`). The next failed a harness assertion that incorrectly capped the table at 4096 entries; upstream supports 16384 (`table-cap-failure.log`). Both harness issues were corrected before the passing run. The decoder's exact-bit behavior on these cases is useful but not a full distribution proof or a reconstructive-matmul correctness/performance test. No challenge submission was made.
