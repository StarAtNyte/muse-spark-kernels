# Current best prefill: direct versus recomputed residual boundary

The public `ruwwww/open-kernel-challenge` repository at commit `c035bf9d5a7d2445d8c8ee5ce49e63b8bb36f49d` uses `BND_RECOMPUTE=False` for long prefill and reports that choice as beneficial. Our newer best prefill source (SHA-256 `f1807a75ec056b7f3874d4fce02331ca0043ac38a45af7710a8287a252421a92`) already implements both strategies and currently enables recomputation. This experiment toggles that existing dispatch only; it copies no code from the public repository. Their reported aggregate score is not evidence of a gain on our source.

The H200 public-image driver measures complete layers for 16,384-token full context 0, sliding context 32768 and full context 65536, two seeds each. It checks both variants against the task reference, retains two baseline captures as an A/A control, and randomizes 16 cold-L2 graph rounds. SGLang is stubbed, attention is pinned, and preparation is limited to the long token count; this is not the official environment. Any lead requires independent validation and the complete official suite. The subprocess is capped at 300 seconds; raw output is in `modal.log`.

Run `ap-dWMgMxhMZxsPUWVDDbLneK` completed with return code 0 and all 18 reference checks passed. Median paired baseline/direct ratios for the two seeds were 0.9924 / 0.9920 at full context 0, 0.9937 / 0.9920 at sliding context 32768, and 0.9961 / 0.9992 at full context 65536. A/A ratios were 1.0002 / 0.9978, 1.0001 / 0.9996, and 0.9946 / 1.0031 respectively. The direct path was consistently slower on the first two cases and not distinguishable from variation in the last; retain recomputation and do not submit this variant. This test does not establish why the other repository reported its result or rule out changes combined with another implementation.
