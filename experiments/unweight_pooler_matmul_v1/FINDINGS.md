# Unweight palette reconstructive pooler screen

On H200 public-image app `ap-w1Dqu7xj4yrN8WF2sVcxzu`, the upstream Unweight codec (`db0e6d3d4505cf71379f6b9b4567acf598bc186c`) losslessly encoded public-reference seed 5151 pooler weights. The screen prepared its palette representation outside timing, launched its palette reconstructive matmul variants 0, 1, 2, 4, 5, 6 and 7 for M128/M256 (variant 3's 192-column alignment does not divide N=4096), and checked each output against the challenge reference. Every tested variant passed for the one input seed per shape. It compared 16 alternating cold-L2 graph replays with `torch.matmul`, not our scored cuBLASLt route.

The fastest tested variant, N1P4 (6), measured 125.57 µs versus 30.85 µs torch at M128, and 125.73 versus 39.47 µs at M256. Other variants were slower. These are raw local timings including event overhead; the screen clearly does not justify promotion, and it does not prove that all possible Unweight implementations or layouts lose. No official submission occurred. The cause of the large regression was not profiled.

The first screen captured the candidate on the wrong stream and thus an empty CUDA graph: its apparent 9–11× gains in `empty-graph.log` are invalid, and its post-eager correctness checks did not validate graph replay. The driver now queries the current capture stream inside the call and rejects empty-graph warnings. A subsequent harness attempt failed with a missing `warnings` import (`missing-import.log`); the final `screen.log` completed with return code 0 and no empty-graph warning. Exact driver and Modal image setup are retained here. Preparation, separate codec costs, wider seed coverage, official correctness, and comparison against the scored route remain outside this screen.
