# Six-bit scale representation feasibility

The scored WGS stage carries 32 KiB of FP4 codes and 4 KiB of E4M3 scale bytes. For a scale group of eight, when every byte is in `0x50..0x8f`, store each byte minus `0x50` in six bits: eight bytes become six. The stage shrinks from 36 KiB to 35 KiB, a 2.78% traffic reduction, provided the packed groups can be transported without extra padding. Arbitrary valid scales outside that range require a full-byte fallback selected during preparation; there is no assumption that inputs follow the benchmark distribution.

`layout.py` exhaustively checks uniform groups for every possible byte, plus 100,000 random in-range groups and all four decoded pairs, against the existing integer scale-pair expression. It is a CPU representation proof, not an FP8 conversion test or GPU kernel. Output: `cpu.log`.

The hard part is access and instruction cost: the current consumer loads eight bytes per lane with one aligned `uint2`, while six-byte groups have alternating 4-byte alignment. Packing two lane groups into 12 bytes or four groups into 24 bytes can restore aligned loads, but requires lane exchange or redundant reads and bit extraction. The existing producer, ring stride, all WGS weight copies, and supported-scale fallback would need coordinated changes. Earlier traffic-only ablation discarded 1 KiB from a stage and found 0.7–1.5% shape-level gains, with invalid outputs by design; that is a screening comparison, not a mathematical upper bound. A real decoder must be measured before integrating this format or using an official check.
