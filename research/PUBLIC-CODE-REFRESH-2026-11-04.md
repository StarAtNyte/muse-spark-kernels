# Public Muse kernel source refresh — 2026-11-04

Search used GitHub repository and code search plus the current public docs. This is not exhaustive, and metadata push timestamps can reflect non-kernel work. Scores below are each author's historical claims, not current standings or proof of rules compliance.

- [AutoclickerI/muse-spark-open-kernels](https://github.com/AutoclickerI/muse-spark-open-kernels), Apache-2.0, HEAD `85aed1fb1365877b615542dd44980646816d6b26`: publicly opened Nov 3. The README reports a 1.8892× decoder and extensive experiments / negative results. Its [final decoder README](https://github.com/AutoclickerI/muse-spark-open-kernels/blob/main/final/muse_decode_layer/README.md) explicitly says the scored artifact expands LZMA/base85 source and contains a nested base64/zlib module. Such a scored artifact conflicts with the current readable-source rule; use the separately unpacked files for research, not the compressed submission. This decoder score is below our 2.23863× readable FP32-storage run, so a wholesale swap is not justified.
- The repository's [findings](https://github.com/AutoclickerI/muse-spark-open-kernels/blob/main/docs/FINDINGS.md) describe their full-verification VQ8 persistent page ring: separate K/V readiness and their tested removal of a redundant wait showed small gains on their implementation; its transfer to our layout is unproven. They also report packed-half exp2 lowers to two MUFU instructions under their CUDA build, consistent with our own paired regression. Their other FA3-like scheduling variants have negative results; compare exact layouts and data dependencies with our `experiments/attention_fa3pp_v1` before spending H200 time.
